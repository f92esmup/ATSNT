# Ephemeral Cloud Batch HPO — Zero Market Data in GCS

Objective: run fetch → HPO → backtest/Monte Carlo on a disposable GCP Cloud Batch Spot VM, keeping market data only on the VM's local disk, while the winning deployment artifact (GCS `artifacts/`) and analytics (BigQuery) survive reliably.
Branch: `feat/ephemeral-batch-hpo` (from `dev`) | Delivery: ask-on-risk (forecast ~700 authored lines → chained PRs decision before T4) | Test runner: `cargo test --workspace`, `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `bash scripts/tests/pipeline_args_test.sh`.

## Specs

- **S1 — Zero market data in the cloud.** User: "No quiero que batch guarde nada de los datos en la nube". Raw zips and Parquet live only on the Batch VM's local disk (`/scratch`); no `gcloud storage cp` of market data anywhere. No `--clean-data` flag: the VM disk dies with the VM, and a local `rm -rf` of the dataset is a hazard (decision L3).
- **S2 — Exact monthly data resolution.** User plan: "cuando se especifique un mes, apunte explícitamente al archivo mensual individual". With `--month <MM>`, `run_hpo` and `backtest` receive `${DATA_PATH}/${SYMBOL}-aggTrades-${YEAR}-${MM}.parquet` (matches `FetchParams::target_parquet_path`); without `--month`, the directory as today. The script fails fast if the resolved file does not exist.
- **S3 — Month-scoped output names.** With `--month`, default config and log names gain the month (`configs/hpo_btcusdt_2026_01.json`, `pipeline_btcusdt_2026_01.log`) so monthly runs do not overwrite each other. Year-only names stay unchanged (keeps `deploy_to_vm.sh` default working).
- **S4 — Container-ready pipeline script.** `--bin-dir <DIR>` skips `cargo build` and runs prebuilt binaries from `<DIR>`. `--dry-run` prints the resolved commands and exits 0 without executing (used by the shell test). New passthroughs: `--strict-sinks`, `--upload-winner`.
- **S5 — Parallel `fetch_data` by month.** User: "habrá que aplicar primero paralelismo a todo lo paralelizable" — refined (L4): only `fetch_data` is parallelized; tick→bar ingestion stays sequential to preserve dollar-bar determinism across file boundaries, and the HPO search is already Rayon-parallel. Bounded concurrency `--jobs <N>` (default 4). Per-item 404 handling replaces the sequential `break`. Output files and final totals are identical to the sequential run; summary lines print in month order.
- **S6 — Per-phase timings.** `run_hpo` prints elapsed seconds for each of its phases (ingestion already does; add splits, search, recording/upload); `backtest` prints elapsed for ingestion, simulation, Monte Carlo, recording. The pipeline script prints total elapsed per stage.
- **S7 — Winner artifact must survive.** User: "quiero que el .json se guarde ya que es importante que los archivos que luego se transmiten al run live/paper o un backtest existan". `run_hpo --gcs-upload` writes `artifacts/<config-stem>-<run-suffix>.json`, where `<run-suffix>` is `BATCH_JOB_UID` when set, else a UTC timestamp. Runs never overwrite each other's artifact. The local `--output-config` file is unchanged.
- **S8 — Sinks fail loudly when strict.** User: "y las subidas a bq para luego revisar resultados si se mantinen no?". BigQuery recording (`run_hpo`, `backtest`, Monte Carlo) and the GCS artifact upload keep their current behavior by default (warn and continue). With `--strict-sinks`, any recording/upload failure exits non-zero after printing the error. Today the GCS upload result is discarded (`let _ =`, `run_hpo.rs:426`) and BigQuery failures only warn (`run_hpo.rs:357`, `main.rs:490`).
- **S9 — Batch container image.** Multi-stage `Dockerfile`: Rust builder (pinned toolchain, release `fetch_data`, `run_hpo`, `backtest`) → `debian:bookworm-slim` runtime with `ca-certificates`, binaries in `/app/bin`, pipeline script in `/app`. `.dockerignore` excludes `target/`, `data/`, `storage/`, `odd/`, logs. Validated locally with a one-day run against `/scratch`.
- **S10 — Batch orchestrator.** `scripts/gcp/run_ephemeral_batch_hpo.sh`: builds and pushes the image to Artifact Registry; renders `job.json` (`provisioningModel: SPOT`, `maxRetryCount: 2`, configurable `--machine-type` and `--region`, sized `bootDisk`, dedicated service account, env `GCS_BUCKET_NAME`/`GCP_PROJECT_ID`); submits; waits via `gcloud batch jobs describe` polling; prints logs via `gcloud logging read` (there is no `gcloud batch jobs logs`); downloads the winner from `artifacts/` into `configs/`. `--dry-run` prints `job.json` without touching GCP. Runs the pipeline with `--strict-sinks --upload-winner --gcp-bigquery`.
- **S11 — GCP provisioning.** `setup_gcp_resources.sh` gains: Batch + Artifact Registry + Logging APIs, an Artifact Registry repo, and the Batch service account with least-privilege roles (BigQuery data editor + job user, object creator on the bucket's `artifacts/` usage, log writer, `batch.agentReporter`).
- **S12 — Measured first run.** One-month job on Batch before any full-year run; record real wall time per phase and cost. Requires explicit user authorization for the remote operation (project, region, machine type). Preflight: machine type availability in the region and CPU/Spot quota.
